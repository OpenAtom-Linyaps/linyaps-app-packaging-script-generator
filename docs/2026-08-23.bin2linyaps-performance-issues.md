## 一、报告要点回顾

`2026-08-22.token-usage-analyze.md` 在 444 个 session 中识别出 **97 个 >400 万 token 的高消耗 session**（占 22%，token 约占全量 49%）。核心结论：

> **高 token 不在"内容多"，而在"回环多"**。思考高度集中在三类行为：
> 1. **构建/监控回环**（bash 高频 + 上下文持续膨胀）
> 2. **技能/路径/接口探索**（路径声明不一致 → 反复定位）
> 3. **校验往返**（版本格式 → edit→validate→read 长回环）
>
> 根因不是内容复杂度，而是模型反复在理解现状、找脚本/路径、配技能调用、验证输出上迭代，把已增长的上文不断重新编码进 input。

## 三、确认的性能问题（含代码定位）

### 问题 1：多策略"搜索"散文驱动技能/路径探索回环（对应报告行为 B）

**报告对应**：`技能加载与脚本接口探索` 主题 606 次命中 / 4.65 亿 token；根因「技能实际路径与声明不一致 → 反复 ls/read/find」。

**代码定位**：
- `agents/deb-linglong-packer.agent.md:210-240`「Workspace 根目錄檢測」——教模型「向上遍历父目录最多 5 层 / 客户端目录搜索」；
- `agents/deb-linglong-packer.agent.md:242-284`「Skills 查找策略」——列出多分支定位方式 + 声称 `.opencode/skills/` 符号链接已就位。

**加重因素**：agent.md 声明的 `.opencode/skills/` 符号链接目录**实际不存在**（仓库无 `.opencode/`），模型按文档找符号链接必然失败、反复定位。

> 多分支 + 遍历性描述，鼓励模型反复寻找 skills 位置，低收益定位往返推高上下文。

### 问题 2：YAML 版本格式校验回环（对应报告行为 C）—— 本仓库已基本消解

**报告对应**：obs-studio 最高 17.3M token；根因「YAML 版本格式反复 edit→validate→read」。

**代码定位（已实现，无需整改）**：
- `skills/bin2linyaps.deb.analyze/scripts/deb_to_linglong.py:336` —— `convert_version_to_linglong()`：去 epoch、去非数字后缀、取前 4 数字段、缺失补 0（`30.2.3+dfsg-3deepin1` → `30.2.3.0`）；
- `skills/bin2linyaps.compat-testing/scripts/validate_linglong_yaml.py:177` —— `MUST_BE_VAR_FIELDS = {"version", "package.version"}` 强制保持 `${ll_version}` 变量，已输出 `Suggested fix:`。

> 版本归一化根因已由脚本确定性消解，无 obs-studio 式手工 edit 试错土壤。**仅需 B2 打磨"输出可执行修复命令"**。

### 问题 3：通用约束在多个文档重复叙述 → 每次加载放大固定上下文

**报告对应**：`每条思考把已增长的上文重新编码进 input`；重复的散文约束推高每个 session 的固定加载量。

**代码定位**（同一约束跨文件重复）：

| 约束 | 出现文件数 | 示例定位 |
|------|-----------|---------|
| wrapper/Desktop Exec/command 机制 | 6 | project-gen、collect-resources、tar.transfer、appimage.transfer、fix + 两个 agent |
| `${ll_version}` 版本保持变量 | 3 | project-gen、appimage.transfer、tar.transfer |
| 模板完整复制 | 4 | project-gen、tar.transfer、appimage.transfer、两个 agent |
| `CI_ll_<package_id>` 命名 | 12 | 全部 skill + 两个 agent |
| base/runtime 白名单 | 3 | project-gen、兼容测试、agent |

> `project-gen/SKILL.md` 1237 行中「错误示例 vs 正确示例」「生成后自检清单」「常见错误警告」**重复 3~4 次**，为最严重冗余。
> multica 平台按 skill 独立下发文件、无法跨目录 import，是约束重复的机制性根因。

### 问题 4：`agent_config_path` 参数漂移（对应报告"技能调用接口与脚本实际 usage 不符"）

## 四、性能影响量化（定性）

| 问题 | 行为签名 | 相关 token 量级（>400 万 sessions） |
|------|---------|------------------------------------|
| 问题 1（探索） | read/glob/skill 高频，穿插 bash find/ls | ~4.65 亿（"技能加载与脚本接口探索"主题） |
| 问题 2（校验回环） | edit 与 read 高频交替 | 本仓库已由脚本派生归一化消解 |

| 问题 5（${tag} 重复） | 每次会话重复 date 工具调用 | 低收益往返 |

## 五、结论

高 token 消耗主要由**可脚本化/文档化的确定性缺陷**驱动，而非内容复杂度：
1. 减少"搜索散文"即可显著遏制探索回环；
2. 版本归一化已下沉脚本（`convert_version_to_linglong()`），无校验回环；仅需校验脚本输出更多可执行修复命令；
3. 约束单一化为专用 `bin2linyaps.constraints` SKILL + agent 一次加载，可显著降低每次加载的固定上下文（尤其 project-gen 1237 行）。

具体改动方案见 `docs/2026-08-23.bin2linyaps-performance-fix-plan.md`。
